# Terraform deployment

Paper and Live are separate root modules with distinct VPC ranges, databases (including PostgreSQL-backed durable queue state), Redis clusters, KMS keys, secrets, IAM roles, and ECS clusters. Deploy them from separate AWS accounts and separate encrypted/locked remote state backends. Never point both roots at the same account-level secrets.

The module explicitly registers an API task plus agent-orchestrator, execution-worker, notification-worker, market-data, and broker-sync task/service boundaries. Each service has its own task role, execution role, log group, least-privilege PostgreSQL login, exact runtime-secret allowlist, read-only root filesystem, and container health check. Durable jobs use the `queue_jobs` table and service-role grants installed by the database policies; Terraform deliberately does not provision an unused parallel SQS control plane. Container Insights alarms track the running consumers whenever worker capacity is enabled. Notification capacity defaults to zero and can be raised only after reviewed APNs identifiers plus its private-key and shared device-token-envelope secrets are provisioned. Live execution and orchestration remain zero by root configuration. All seven release flags are rendered false into every task; Terraform is not authorized to turn them on.

Paper orchestration also requires active market-data capacity, an HTTPS provider URL, and a configured `MARKET_DATA_PROVIDER_ID` present in `APPROVED_MARKET_DATA_PROVIDERS`. Hermes research is isolated to agent-orchestrator: capacity is rejected unless the endpoint and model exactly match the reviewed WHOX values and an operator attests that the dedicated profile is stateless with terminal, file, web, memory, skill, plugin, MCP, cron, and delegation capabilities disabled at the provider. Scheduler lag is surfaced in worker health and converted from the redacted `paper_scheduler_lag` event into a CloudWatch alarm. Market-data and Hermes bearer keys remain available only to their exact consuming services; no model process can read the broker token vault.

Each root declares the S3 backend but intentionally commits no bucket/account configuration. Copy that environment's `.backend.hcl.example` to the ignored `.backend.hcl` name, replace every placeholder, and provision the bucket/KMS key outside this stack. Paper and Live must use different AWS accounts, buckets, KMS keys, state keys, and deployment roles. The examples require S3 encryption and Terraform's native state lockfile; bucket versioning and restrictive bucket/KMS policies are also mandatory.

```sh
terraform -chdir=infrastructure/terraform/environments/paper init -backend-config=paper.backend.hcl
terraform -chdir=infrastructure/terraform/environments/paper validate
terraform -chdir=infrastructure/terraform/environments/paper plan -var-file=paper.tfvars
```

Copy the matching `.tfvars.example` to the ignored `.tfvars` filename and replace every placeholder. CI syntax validation uses `terraform init -backend=false`; it does not contact or validate a deployed backend. Supply image digests rather than mutable tags. Supply `redis_auth_token` through the deployment secret channel, not a committed file. Because Terraform must send that value to ElastiCache and the managed `REDIS_URL` secret version, it persists in Terraform state. An encrypted, access-controlled, versioned, locked remote state backend is therefore mandatory; local state is prohibited for Paper and Live.

## Runtime-secret and database-role bootstrap

The first apply must keep `runtime_secrets_bootstrapped = false`. That forces API and worker desired counts to zero while creating the infrastructure and empty secret containers. Terraform creates separate database URL containers for API, App Store notifications, agent orchestration, execution, notifications, market data, and broker sync, plus `session-signing-secret`, `pairing-hash-pepper`, `rate-limit-key-secret`, `device-token-encryption-key`, `apple-root-ca-bundle`, `apns-private-key`, `market-data-provider-token`, and `hermes-api-key`. It creates the complete TLS `REDIS_URL` secret itself. The RDS-managed master secret is output only as the sensitive `database_bootstrap_secret_arn`; no ECS execution or task role can read it, and it is never injected into a container.

Using the controlled database-administration workflow:

1. Use the RDS master secret only from an audited one-off migration/bootstrap identity, never from an application task.
2. Run migrations, create a distinct login role per runtime, and grant exactly one matching NOLOGIN group: `whox_api_runtime`, `whox_app_store_notifications`, `whox_agent_worker`, `whox_execution_worker`, `whox_notification_worker`, `whox_market_data_worker`, or `whox_broker_sync_worker`. The values must be complete `postgresql://...` URLs with TLS required; do not connect as the migration/master role or store split host/user/password fields.
3. Put those URLs into their matching Secrets Manager containers. Populate four distinct random values of at least 32 bytes for `SESSION_SIGNING_SECRET`, `PAIRING_HASH_PEPPER`, `RATE_LIMIT_KEY_SECRET`, and `DEVICE_TOKEN_ENCRYPTION_KEY`. Populate the Apple PKI root-certificate bundle from Apple's official certificate authority distribution; never persist raw StoreKit JWS payloads.
4. If market-data capacity is requested, use an approved HTTPS provider URL and populate its token secret. Before raising agent-orchestrator capacity, rotate any Hermes key previously shared through chat or another non-secret channel, inject the replacement directly into `hermes-api-key`, create the dedicated tool-free/stateless profile, independently verify its configuration, and only then set `hermes_research_profile_tools_disabled = true`. Before raising notification capacity, populate the APNs private-key secret, use the same device-token encryption secret in the API and notification worker, and record review of the Apple team ID, key ID, bundle topic, and sandbox/production selection. Terraform rejects incomplete public APNs/Hermes configuration, while each worker rejects absent or malformed secrets at startup.
5. Verify secret versions, database grants, migration state, health checks, image digests, and the plan. Record that evidence in the deployment change, then set `runtime_secrets_bootstrapped = true` in the environment's secret configuration and apply again.

The API execution role can inject only its tenant and isolated App Store database URLs, `REDIS_URL`, `SESSION_SIGNING_SECRET`, `PAIRING_HASH_PEPPER`, client-address rate-limit HMAC secret, device-token-envelope key, and Apple root-certificate bundle. Each worker execution role can inject only its own service-specific `DATABASE_URL` and `REDIS_URL`; agent-orchestrator alone receives the Hermes key, market data alone receives its provider token, and notifications receive only the shared device-token key and APNs signing key. Only the execution-worker and separately reviewed broker-sync task roles can read the broker token vault at runtime; the API and orchestrator have neither `secretsmanager:GetSecretValue` nor KMS decrypt access to it. Exact public/admin/connect URLs, CORS origins, and health ports are attached to the appropriate tasks. PostgreSQL queue state remains private within each environment database; the only public entry point is a TLS ALB protected by WAF. The environment KMS policy grants the regional CloudWatch Logs service access only when the encryption context names that environment's `/whox/<environment>/*` log groups.
